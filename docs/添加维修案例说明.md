# 添加维修案例说明

案例数据维护在 **`src/lib/config.js`** 的 `repairCases` 数组中。  
首页展示最新 12 条，全部案例在 **`/cases`** 按**小区 / 地点**分组导航。

---

## 一、字段格式（公开展示）

```js
{
  date: '2026-07-17',       // YYYY-MM-DD，决定排序（新→旧）
  tag: '车库门',             // 短标签：门类或处置类型，如 电机更换 / 控制器 / 换锁
  location: '东瑞小区',      // 标准地点名，见下文「命名规范」
  title: '一句话标题',       // 故障 + 处置，便于列表扫读
  desc: '故障现象 → 判断 → 处理', // 面向客户的通顺中文，勿写金额与介绍来源
}
```

**不要写入公开展示文案的内容：**

| 勿写 | 原因 |
|---|---|
| 流水 / 利润 / 成本 | 隐私与商务敏感 |
| 客户姓名、手机号 | 隐私 |
| 抖音 / 二嫂 / 同学等来源 | 已统一剔除；内部账可另记 |

**应写入的内容：**

- 门类、地点（标准名）、现象、判断、处理结果  
- 若同一小区内场景需区分（如「库房」「门市」），写在 **title / desc** 里，不要拆成新的 `location`

---

## 二、地点（小区）命名规范

`/cases` 左侧导航按 **`location` 字符串完全一致** 才合并。  
名称多一个字都会变成两个导航项。

### 强制规则

1. **同一小区 / 同一片区只用一个标准名**  
   - ✅ `佳润花园小区`  
   - ❌ 再拆 `佳润花园小区库房`、`佳润花园`、`佳润花园小区车库`
2. **场景细节写进 title/desc**  
   - 例：`title: '小区库房门卡住上下不动复位'`  
   - 例：`desc: '…佳润花园小区库房反映…'`
3. **优先复用已有名称**，不要随手造近义名  
4. **商业街 / 村 / 厂** 同样：能合并到已有条目则合并，不要「材料街」与「材料街门市」并存

### 历史曾合并的示例

| 旧名称（勿再用） | 标准名称 |
|---|---|
| 佳润花园小区库房 | **佳润花园小区** |
| 新天地 | **新天地商业街** |

### 易混但默认**不**自动合并（需人工确认）

这些名字相近，但可能是不同地方，**不要擅自合并**，应询问用户：

| 名称 A | 名称 B | 说明 |
|---|---|---|
| 福瑞祥 | 福瑞小区 | 用字不同，可能两处 |
| 福瑞小区 | 福祥小区 | 用字不同 |
| 福星家园 | 福祥小区 | 不同小区 |

## 三、添加前必做：检索 + 询问（给维护者 / AI 助手）

每次往 `repairCases` 增加案例时，**在写入前**按顺序执行：

### 步骤 1：列出候选地点名

从用户口述中抽出地点，如「佳润花园库房」「东瑞」「新天地门市」。

### 步骤 2：在现有数据中检索

在 `src/lib/config.js` 的 `repairCases` 里检索 `location` 字段，至少做：

1. **完全匹配**：已有同名 → 直接用该 `location`  
2. **包含 / 被包含**：如「佳润花园」与「佳润花园小区」「佳润花园小区库房」  
3. **去后缀近似**：去掉「小区 / 村 / 商业街 / 门市 / 库房 / 厂」后比较是否相同或高度相似  
4. **同音近形**：如福瑞 / 福祥 / 福星（仅提示，不自动合并）

可用命令辅助（在项目根目录）：

```bash
# 列出全部已有地点及条数
node --input-type=module -e "
import { repairCases } from './src/lib/config.js';
const m = {};
for (const c of repairCases) m[c.location] = (m[c.location] || 0) + 1;
console.log(Object.entries(m).sort((a,b)=>b[1]-a[1]||a[0].localeCompare(b[0],'zh-CN'))
  .map(([k,v]) => v + '\t' + k).join('\n'));
"
```

或全文搜索：

```bash
rg "location: '" src/lib/config.js
```

### 步骤 3：若发现相似地点 → **必须先问用户**

**禁止**在未确认时自行新建一个接近但不相同的 `location`。

询问模板示例：

> 现有案例里已有地点：**「佳润花园小区」**（N 条）。  
> 本次您写的是：**「佳润花园小区库房」**。  
> 是否合并到 **「佳润花园小区」**？（库房信息写进标题/正文）  
> 还是保留为独立地点名？

用户确认后再写入。

### 步骤 4：插入位置与排序

- 新案例插入 `repairCases` **数组靠前**（日期最新的在最前）  
- 同一天多条：保持合理顺序即可（如上午在前或按录入顺序）  
- 日期格式统一：`YYYY-MM-DD`

### 步骤 5：自检

- [ ] `location` 与已有标准名一致（或用户明确要求新建）  
- [ ] 无金额、无客户来源  
- [ ] `desc` 为「现象 → 判断 → 处理」  
- [ ] 本地或构建预览 `/cases` 导航是否归入预期小区

## 四、从用户周记草稿到正式条目（示例）

**用户草稿：**

```text
7.6 车间大门  佳润花园小区库房
原因：卡住了 上不来下不去 复位进槽
```

**检索：** 已有 `佳润花园小区` → 询问是否合并 → 用户同意。

**写入：**

```js
{
  date: '2026-07-06',
  tag: '车间大门',
  location: '佳润花园小区',  // 合并后的标准名
  title: '小区库房门卡住上下不动复位',
  desc: '佳润花园小区库房反映卷帘门卡住、上不来下不去。现场查为门体脱出导槽，重新顺槽复位入槽后，开关恢复正常。',
}
```

## 五、与 GEO / 展示的关系

- 地点名统一 → `/cases` 侧栏更干净，同一小区案例聚在一起  
- 标题/正文带「枣强 + 小区名」→ 利于「某小区修门」类检索  
- 勿为 SEO 故意拆多个近似地点名（会稀释、也难维护）
